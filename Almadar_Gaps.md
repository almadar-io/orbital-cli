- **G-ORBITAL-CLI-008** [mechanical] — Nine CLI integration tests are red because their fixture programs predate validate rules added since: `relative_lolo_imports` (2), `validate_compile_error_json` (2), `live_registry` (2) and `native_shell_mixed_resolved_schema` (3) expect `valid: true`, and their programs now fail `ORB_ENTITY_WRITE_UNDECLARED` / `ORB_ENTITY_READ_UNDECLARED` (no `@create`/`@read`), `ORB_FETCH_UNBOUNDED` and `ORB_EFF_SERVER_EFFECT_NO_FAILURE_ROUTE`. The rules are right; the fixtures need their policies, limits and failure routes declared. Seen 2026-11-15 running the suite for P-034 memory round 2 (unrelated to it). Also, seen 2026-11-16: the unit test `program_host::tests::read_with_findings_surfaces_the_l1_warnings_the_lowered_program_loses` expects one finding for `app Foo "1.0.0"`, but `source_findings` (`utils/validation.rs`, full `parse_str`) has also reported `ORB_L_APP_HEADER_DESCRIPTION_MISSING` for a header with no description since 2026-11-07; the test's headers need a `description:`. Reproduce: `cargo test -p orbital-cli --test it validate_compile_error_json`. Prevention rung: (3) the verifiers (the suite run at each rule change). Severity: medium. Root cause: one-off.


- **G-ORBITAL-CLI-005** [mechanical] — While the catalog is browsed, the launchpad spends its CPU re-reading `.lolo` source. samply on the launchpad process over 80 catalog page opens (`orb profile launchpad --samply`, 2026-11-13, 100 Hz, each thread's pre-recording CPU left out) ranks by self CPU: `orbital_lolo::lexer::Lexer::run` 7.5 s, `Vec::from_iter` 2.8 s, SipHash and `HashMap::insert` about 4 s, file opens, `getdirentries` and `stat` about 4.5 s, brotli compression of responses 1.2 s, `drop_in_place<Parser>` 0.6 s; the counting allocator (`alloc_meter::count`) 0.9 s. So each guest open lexes and parses source files again, about 90 ms of lexer time per open. Attributed 2026-11-16 (samply over a catalog tab plus std-kflow and orb-medar-home opens, 24 s of server CPU, `.lolo` work 2.7 s):
  - **Catalog listing, 1.3 s. Fixed the same day:** each tab's `behavior/catalog` called `parse_app_header` for each of 2,823 behaviors, and it lexed the whole file and copied it into a char vector. orbital-lolo now walks the source in place and lexes a header read on demand (`LazyTokens`; tests in `parser::tests`: a body that does not lex leaves its header readable, with controls). The listing is identical; user CPU went 0.75 → 0.30 s.
  - **Compose and describe, 583 ms. Changed the same day, gain not yet seen:** `reflect::resolve_from` built a fresh compiler loader per call. Now:
    - it keeps the 8 most recent loads, each with the files its load read, and answers again only while they are unchanged (`reflect::tests`);
    - the compiler loader reloads a cached load whose files changed (`loader::tests`); it used to serve a stale program.

    A warm re-profile still lowers about 640 ms in compose and describe, so those loads did not hit. The likely cause, not confirmed, is std files and folders being edited by other sessions during the run, which changes their read sets. Next: the resolve-cache debug log, which needs a 4790 restart.
  - **Resolve, 524 ms:** gone on the warm re-profile.

  Re-profile after the change, same sequence: server CPU 24.4 → 19.6 s, `.lolo` work 2.7 → 1.0 s, catalog headers 1.3 → 0.35 s. Owner: orbital-cli (program_host's behavior/* answers) with orbital-lolo. Reproduce: `ORB_CHROME=<chrome> orb profile launchpad --limit 80 --pid <launchpad pid> --samply`. Prevention rung: none (a cost, not a wrong result). Severity: medium. Root cause: one-off.

- **G-ORBITAL-CLI-004** [mechanical] — `orb-dev lower` exits 0 when it cannot lower: a missing file or a `.lolo` parse error prints the error but the exit status is 0, so a script that checks the status reads a broken file as fine. Seen 2026-11-13 (`orb-dev lower /dev/null/x.lolo; echo $?` prints 0). Fix: a failed lower exits non-zero, as validate does. Prevention rung: none (tooling). Severity: medium. Root cause: one-off.

- **G-ORBITAL-CLI-003** [mechanical] — `orb-dev signatures` fails inside a workspace package: run from `packages/almadar-std` or `packages/almadar-behaviors` it answers `os/read-file: …/node_modules/@almadar/core/package.json resolves to …/orbital-rust/crates/orbital-shell-typescript/core/package.json, outside the grant`, because pnpm links `@almadar/core` to the workspace and the command's file grant covers only the package's own tree. `orb-dev reference` from the same folders works, and `orb-dev signatures` from the monorepo root works, so only the signatures command's grant differs. Seen 2026-11-12. Reproduce: `cd packages/almadar-std && orb-dev signatures`. Fix: the signatures command reads the installed core through the same resolution `reference` uses (follow the package link, granted as the resolved root). Prevention rung: none (tooling). Severity: medium. Root cause: one-off.
- **G-ORBITAL-CLI-001** [mechanical] — `orb serve <program>` scaffolds a whole app (~100 MB: kernel, packages, lockfile) under `<cwd>/.orbital/serve/<name>` per program and never removes or reuses it across programs, so a batch that serves many programs fills the disk (the H4 parity gate reached ~336 GB on 2026-11-06 before the gate learned to delete it per pair). Owner: orbital-cli serve. Fix: share one scaffold (the program is the only per-run file) or remove the scaffold on exit. Prevention rung: none (resource hygiene). Severity: medium. Root cause: one-off.
